# Aion private staging backup and recovery

This workflow covers the private ARM64 staging deployment and exercises FR-026 and NFR-011–012. The recovery target is 24 hours of database writes and eight hours of operator recovery time. Restore into a disposable project with all API traffic and mail delivery disabled until reconciliation finishes.

## Backup schedules and access

- Take a PostgreSQL custom-format logical snapshot at 06:00 and 18:00 UTC. This leaves time to respond to a missed backup before its age reaches 24 hours. Store the database dump, release configuration and image manifest in private S3 with 30-day expiration. Keep the original release archive under `releases/<source-revision>/aion-staging.tar.gz` while any snapshot references it. Record the package SHA-256 separately and verify it before loading the images.
- Store its credentials, TLS material and application keys in a separate private S3 bucket with the same expiration. Encrypt this bundle using CMS and the recovery operator's public certificate before uploading. The corresponding decryption key stays off the EC2 instance. Keep a separately protected copy of that key and test access before relying on the backup. Rotate the certificate with its recipient key retained through the expiry of any matching backups.
- Export the deletion UUID, keyed email identifier, marker timestamps and suppression reason to a third bucket every five minutes. Operational markers outlast database snapshots; review their retention annually. Synthetic rehearsals use `drills/` under each object prefix and expire after 30 days. Keep the application key material independent of the marker bucket.
- Use bucket-owner-enforced, encrypted storage with public access blocked. Give the staging instance permission to create objects in the named prefixes. The recovery operator retrieves them with a separate identity. The instance has no backup read or delete rights.
- Observe both systemd timers and the CloudWatch backup signals. Missing signals raise alarms routed to the operator queue. Check the age of successful objects alongside the alarm state. A positive metric follows successful upload. For staging, inspect the queue in the AWS console. Verify the production operator delivery channel separately.

Install the scripts from `deploy/staging/recovery/` in `/opt/aion-staging/recovery` and the units in `/etc/systemd/system`. Set the root-owned `backup.env` from the installed release and the operator's private staging configuration: `AION_BACKUP_BUCKET`, `AION_KEY_BACKUP_BUCKET`, `AION_RECOVERY_BUCKET`, `AION_RECOVERY_REGION`, `AION_RECOVERY_ACCOUNT`, `AION_STAGING_RELEASE_DIR`, `AION_STAGING_STATE_DIR`, `AION_RECOVERY_WORK_DIR`, and `AION_RECOVERY_RSA_KEY` (the public recipient certificate). Load the AWS CLI image pinned in `backup.sh` into Docker before starting the units. Run `systemctl daemon-reload`, then enable and start `aion-staging-backup.timer` and `aion-staging-markers.timer`. Start both corresponding `.service` units once and check the journal, uploaded objects, alarms and queue before relying on the schedule.

Keep the configured release path and independently stored image archive current when changing staging releases. Rehearse recovery and update the recovery schema checks when a release introduces a migration.

## Write-ahead journal for account host loss

When journaling is enabled, the API waits for an encrypted, conditional S3 write before committing an authorized deletion or new mail suppression. The relay stores an account UUID and keyed identifiers with a timestamp. A timeout returns a retryable `503`. A write that reached S3 before a lost response or failed SQL commit still carries the authorized operation. Recovery applies that intent, including when the source database never recorded it.

1. Freeze account and suppression writes. For a first activation, use `capture.py markers` to capture the frozen database markers and application-key fingerprint. Create a fresh epoch (32 lower-case hexadecimal characters). Add its value as `journal_epoch` in the capture and upload it as `markers/journal/<epoch>/baseline.json` with `If-None-Match: *`, SSE-S3 and a SHA-256 checksum. Use `markers/drills/journal/` for isolated rehearsal objects. Verify the baseline independently from the operator identity before lifting the freeze.
2. Store that epoch in `journal-epoch` inside the private state directory. Keep the directory mode 0700 and the file mode 0444 for the container bind. The API, relay and snapshot tool share this file. Start the supplied `aion-staging-journal.service` on the staging host. Use `deploy/staging/compose.journal.yaml` with the reviewed staging Compose and image settings. Verify relay startup and a test acknowledgement, and take an epoch-stamped snapshot before admitting writes. Use a separate state directory and storage scope for a public environment. Retain the baseline and all of its journal records for the lifetime of every recoverable snapshot in the epoch.
3. After loss, fence the source before listing objects. Stop or isolate the old API, workers and replay jobs, ensure it cannot resume database writes and account mail, and confirm committed journal writers are finished. Record the last possible commit time from the operator timeline. Keep the new service closed while independently collecting the full prefix. The journal tool validates the baseline and each object against the expected epoch, application-key fingerprint and checksum. S3 provides strongly consistent listing of completed writes. [Amazon S3 consistency](https://docs.aws.amazon.com/AmazonS3/latest/userguide/)

   ```sh
   python3 deploy/staging/recovery/collect_journal.py \
     "$MARKER_BUCKET" "$AWS_REGION" "$BUCKET_OWNER" "$JOURNAL_EPOCH" \
     "$SNAPSHOT_KEY_FINGERPRINT" INPUT_DIR/markers.json --fenced-at "$WRITE_CUTOFF_UTC"
   python3 deploy/staging/recovery/restore.py \
     INPUT_DIR NEW_DIRECTORY aion-recovery-drill --through "$WRITE_CUTOFF_UTC" --require-journal
   ```

   The restore applies the independently collected deletion and suppression records and blocks verification dispatch for the rest of the current UTC day because an older snapshot may undercount attempts. Continue with the isolated API probes below before resuming account traffic.
4. After recovery or planned epoch replacement, repeat the freeze. Collect the complete previous journal and replay every outstanding intent before preparing the new baseline. Preserve the previous epoch with its matching snapshots and keys until they expire. Verify a new snapshot with the new journal before lifting the freeze. Keep traffic and sends paused whenever coverage is uncertain.

## Rehearse an isolated restore

1. Record the start time and the last time the lost database could have accepted writes. For a journaled source, fence it and collect the epoch as described above. For a planned legacy staging drill, pause database writers, mail workers and ingress, then publish a final independent marker copy. Use its timestamp only when it follows an independently confirmed write freeze. Keep account traffic and mail paused when marker coverage ends before the cutoff.
2. From an operator identity, download the selected `snapshots/<id>.tar.gz` and its matching `keys/<id>.cms` from separate buckets. Verify the journal or legacy staging marker copy matches the application-key fingerprint and covers the cutoff. Download the exact release archive, verify its recorded checksum and load `images.tar` from the archive on the recovery host. Also make the pinned PostgreSQL image available there. From an owner-private directory, decrypt the key bundle into `keys.tar.gz` alongside `snapshot.tar.gz` and `markers.json`.

   ```sh
   umask 077
   openssl cms -decrypt -binary -inform DER -in keys.cms \
     -recip "$RECOVERY_CERT" -inkey "$RECOVERY_KEY" -out keys.tar.gz
   ```

3. Run `python3 deploy/staging/recovery/restore.py INPUT_DIR NEW_DIRECTORY aion-recovery-drill --through WRITE_CUTOFF_UTC`. Add `--require-journal` for public account recovery. Use Python 3.12 or later. The script verifies the dump and key bundle hashes and application key fingerprint. Only a new isolated PostgreSQL volume starts. The script applies current deletion and suppression markers, clears sessions and authentication challenges, and safely cancels pending mail. The runtime role can access application tables and read the migration version after restore. A failed check leaves the restored database isolated.
4. Verify that a known deleted UUID and its dependent data are absent, recovered deletion and suppression markers remain, old session cookies and codes fail, and surviving accounts cannot read each other's profiles. Exercise the reviewed API against the isolated database with capture mail, Resend and scheduled reminders disabled. Start no worker and publish no port. The synthetic fixtures in `seed-drill.sql` and `probe-drill.py` support this sequence: seed an empty source, run the `prepare` probe in the source API container, take the snapshot, run `delete` in that container, stop it, and copy the markers. Run the `restored` and `rollback` probes in the respective isolated API containers with `docker exec -i CONTAINER python - PHASE < deploy/staging/recovery/probe-drill.py`.
5. Rehearse switching between two artifacts verified against the restored schema. Recheck the database revision and restored profiles after switching back. Before resuming public account writes, confirm the chosen artifact enforces the same journal and mail guards. Use maintenance mode if the available rollback artifact cannot do so or has an incompatible schema.
6. Record the snapshot age at the write cutoff, the marker lag and the elapsed time through verification. Report remaining host, operator and production prerequisites. Remove disposable projects and decrypted drill files when finished.

## Private staging rehearsal evidence

On 2026-11-14, an isolated EC2 source captured a snapshot of three synthetic accounts, then deleted one through the API and recorded a separate synthetic bounce. The source was removed after it uploaded the independent markers. An isolated OrbStack database recovered the S3 snapshot, keys and markers. The old UUID was present in the snapshot and absent after reconciliation; the deletion marker and suppression survived. Old session cookies and a previously valid, browser-bound code were rejected. Both surviving accounts could read their own profiles and received `409` for each other's. The stale verification queue was empty, the pending reminder with an unknown delivery outcome was marked uncertain with no payload, and its schedule was paused. A copy of the markers that did not cover the requested cutoff was rejected before PostgreSQL started.

The snapshot was 5.5 seconds old at the controlled write cutoff. With the verified S3 release images already loaded, recovery through API verification took 24 seconds. Switching from a synthetic compatible candidate to the preserved staging image took another 6 seconds; the database volume, schema, and verification results were unchanged. These timings describe a small, planned drill. No worker or mail transport ran during it.

In a separate EC2 rehearsal, the API deleted a synthetic account and processed a signed synthetic bounce after the snapshot. The disposable source and its volume were removed without a final periodic marker export. The operator retrieved the frozen baseline and both event records from S3, verified their checksums and restored on OrbStack. The journal kept the deleted account out and retained the bounce suppression. Stale sessions, codes and work were rejected or cleared, and surviving profiles remained isolated. Recovery rejected a changed event and a cutoff beyond the verified fence. The verification-mail budget was held for the rest of the UTC day. A second rehearsal verified relay restart with a stale socket and rejection of snapshot capture when the live API's journal epoch file was missing.

Verify the production backup identity, recovery key custody, exact application artifacts and on-call alert delivery with the operator before enabling public accounts.
