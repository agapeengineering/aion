# Aion R2 — optional accounts, sync and email reminders

Version: **1.0.0**. Status: **Accepted R2 baseline — local foundation implemented; account release not implemented or deployed**. Accepted: 2026-10-17. Owner: Agape Engineering.

This accepted amendment specifies the first Aion backend and the corresponding web changes. The [R1 specification](web-release-specification.md) and [0.1.0 release record](../releases/0.1.0.md) describe the existing local-only release. The [foundation verification record](../testing/backend-foundation.md) describes implemented local health/schema/container groundwork; accounts, sync, mail and infrastructure migration remain unimplemented. [ADR-0002](../architecture/decisions/0002-optional-account-backend.md) supplies the deployment design. Requirement acceptance is distinct from implementation evidence.

## Purpose and scope

Let a person optionally verify an email address, save their calendar settings to an account, recover those settings on another device, and receive an explicitly requested daily or weekly reminder. Guest use remains free, local and complete. Email is a dated reflection on a chosen lifespan, never a prediction or a live countdown.

Must/R2: email-code account creation/login; revocable sessions; one calendar profile per account; explicit initial import; revision-based sync with visible failure/conflict handling; daily/weekly optional reminders; EN/ES parity; unsubscribe; account export/deletion; secure and recoverable containerized deployment; migration of the existing web app to the same-origin EC2 topology. Every requirement below is Must/R2 unless marked otherwise.

Still excluded: mandatory accounts, passwords/social login, multi-user calendars, shared profiles, AI, journal/goals/streaks, ads/paid tiers, analytics/open/click tracking, attachments, browser push notifications, native clients/widgets/automatic wallpaper and high availability. Email-address changes/account merging and custom reminder units are Later; deleting/recreating an account is not an email-change mechanism that transfers identity. Loss of mailbox access has no manual identity-bypass recovery in R2.

### Journeys

1. **Guest:** existing setup, local persistence, calendar, ticking, visibility and PNG export continue without contacting the API or email provider. Choosing sign-in is explicit.
2. **First account:** enter email → receive code → verify → choose whether to save the current local calendar, create a profile, or remain unsynced. Account creation alone does not upload a birth date or enable reminders.
3. **Another device:** verify email → load existing account profile → show the calendar. If this device already has different guest settings, ask which to retain; never silently replace either copy.
4. **Reminder:** verified account with saved profile → enable daily/weekly → select timezone/time/language/phrase → save consent → receive dated emails → disable in settings or unsubscribe without signing in.
5. **Exit:** sign out clears the account cache from this browser; export downloads account data; recent re-verification plus confirmation deletes the account and stops queued sends.

## Functional requirements

| ID | Required behavior | Acceptance cases |
| --- | --- | --- |
| FR-014 | Preserve optional guest mode and explain account data handling before signup/import. | R1 setup/edit/reset/export works without API calls even during backend outage. Account/privacy UI distinguishes local saving, successful cloud saving and optional mail. Signup does not upload the guest profile. |
| FR-015 | Create/access accounts through passwordless email verification. | One normalized email identity; trim whitespace, use a documented case-insensitive identity policy without provider-specific dot/plus rewriting. Always return a generic request response regardless of account existence. Defaults: cryptographically generated 8-digit code, 10-minute expiry, five attempts/challenge, 60-second resend cooldown, three send requests/email/hour and 20/IP/hour. Resend invalidates the previous challenge. Bind code to an opaque challenge and initiating browser; verify/consume atomically, reject replay/expiry, never create an authenticated session from a GET/link visit. A successfully verified first login creates the user; no unverified account receives sync/reminders. Rate limits persist across API restarts and cannot be bypassed by requesting a new challenge; bound failed attempts across challenges/email/IP too. |
| FR-016 | Manage revocable browser sessions. | Opaque high-entropy server sessions with only token digests stored; Secure/HttpOnly/SameSite=Lax, host-only cookie, CSRF and Origin validation on state changes. Rotate on login; reject session fixation. Expiry: seven days idle, 30 days absolute. List sessions with creation/last-use time; revoke another session or all sessions; sign-out revokes the current one. Never expose tokens to JavaScript, URLs or public logs. Account export/deletion requires email re-verification within the preceding ten minutes. |
| FR-017 | Store one versioned profile owned by the current user. | Store date of birth, positive integer lifespan, language, primary unit and hide-remaining flag; validate all fields and supported Gregorian range with the existing contract. Authorization derives user identity from the session, never a submitted owner ID. Unique user/profile relationship; reject invalid or unsupported versions without overwriting. Store settings, not a per-second countdown or a history of every tick. |
| FR-018 | Resolve initial device/account data explicitly. | If no account profile exists, offer upload of this device's valid settings or new setup. If account profile exists and this device has different guest data, show a comparison and require use-account or replace-account confirmation. Choosing account data preserves the guest record separately until explicit guest reset. Replacing uses the current server revision; an intervening edit returns a conflict. No reminders are enabled by import. |
| FR-019 | Synchronize complete profiles without silent data loss. | Return a monotonic revision/ETag; require the last-read revision for every write/reset. Concurrent stale writes return 409 with the current profile/revision; show keep-server or explicitly reapply-device choices. No automatic last-writer-wins or field merge. Repeated writes use an idempotency identifier; a retried operation cannot overwrite newer data. Read on sign-in, page foreground and before writes, and poll no faster than once/minute while signed in/visible/online. No WebSocket requirement. |
| FR-020 | Support offline account viewing/editing honestly and isolate caches. | Already loaded cached calendar and local PNG export keep working. Queue one latest desired profile per account with its base revision; show pending/failed status. On reconnect revalidate session and fetch server revision before upload; resolve conflicts under FR-019. Never upload to a different account or after sign-out. Expired/revoked sessions cannot sync. Sign-out warns before discarding pending edits, then clears this browser's account cache; it does not auto-convert private account data into guest settings. A remote revocation cannot erase an already offline device; disclose this limit. |
| FR-021 | Distinguish local clearing, calendar reset and account deletion. | Guest reset retains R1 behavior. Clearing a signed-in browser signs out and removes its account cache. Resetting the account calendar requires online confirmation and a current revision; atomically removes the saved profile, disables reminders and cancels pending reminders. Other signed-in clients clear their cached profile when they next refresh. Deleting the account is separate FR-026 behavior. Do not replay an offline reset as an unreviewed destructive action. |
| FR-022 | Provide verified, explicitly opted-in reminders. | Off by default; require a saved profile and explicit consent. Choices: daily or weekly; IANA timezone; local send time; weekday for weekly; EN/ES; include phrase on/off. First-selection defaults: weekly, Monday 09:00, detected timezone shown for confirmation, profile language, phrase on. Store consent time and notice version. Preferences are edited online with revision checks; server confirmation is required before claiming enrollment/change/pause succeeded. Signing out does not unsubscribe; explain this. |
| FR-023 | Render calm, accurate email snapshots. | HTML and plain-text EN/ES; date/timezone, chosen lifespan caveat, lived/remaining weeks, and optional phrase from the shared original bank. Remaining figures are omitted when the saved hide preference is true. Beyond horizon: remaining clamps to zero, lived continues, non-predictive copy. Omit literal birth date and personal figures from subjects/preheaders/URLs. No live ticking, tracking pixels, click tracking or attachments. Include app link, unsubscribe and a real configured support route. Preview sample content with synthetic data before enabling. |
| FR-024 | Schedule durable reminders with bounded duplicate/stale delivery. | Worker checks due schedules at least every 60 seconds; persists UTC next-due plus local scheduling rule. Spring gap: next valid local time; fall fold: first occurrence only. At most one logical reminder per account/local calendar date, including preference changes/restarts. A weekly reminder uses the selected weekday, not a fixed 168-hour interval. Eligible reminders expire one hour after their intended time; downtime does not produce a backlog. Enabling/changing a schedule targets the next future occurrence, never an immediate retrospective send. Claims use expiring leases; crash recovery and concurrent worker runs cannot create duplicate logical jobs. Recheck active consent, account/profile, suppression and saved visibility before dispatch; cancel an obsolete queued payload rather than sending stale private content. |
| FR-025 | Allow unsubscribe and react safely to delivery events. | Every reminder supports a narrowly scoped unguessable unsubscribe token: browser GET shows confirmation; confirmation POST and standards-compatible one-click POST disable reminders without login. Repeated POST is harmless; GET must not change state because mail scanners follow links. Atomically disable enrollment and cancel pending reminders; transactional sign-in mail remains available unless delivery-suppressed. Verify provider webhook signatures over the raw body, reject replay outside the verifier's tolerance, deduplicate event IDs and persist processing before 2xx acknowledgement. Hard bounce/complaint suppress sending to that address; out-of-order delivery events cannot undo suppression or opt-out. |
| FR-026 | Support account export/deletion and stopping sends. | Recent email re-verification; export a versioned JSON containing profile and reminder/consent settings, without session secrets. Deletion requires explicit confirmation, revokes all sessions, cancels pending sends and removes active identity/profile/settings/challenges/outbox content in one transactional workflow. The browser clears its account cache; other devices clear on next successful auth check. Provider-accepted mail cannot be recalled. Isolate in-flight sends through a per-account claim/dispatch barrier; no new dispatch may begin after deletion/unsubscribe is committed. Record independent minimal deletion markers for backup reconciliation; see retention. |

## Data and retention contract

Logical entities: `users`, `sessions`, `email_challenges`, `profiles`, `reminder_preferences`, `email_outbox`, `email_events`, `email_suppressions`, and a minimal deletion ledger. Tables may be consolidated where constraints and tests remain clear. No administrative UI, general-purpose user search or journal data is required.

| Data | Retention/handling |
| --- | --- |
| Account email and current profile/preferences | While account exists; deleted from active application stores on successful deletion. Email change is not supported in R2. |
| Session credentials and verification codes | Store only appropriate digests; low-entropy codes require keyed protection, not an unsalted fast hash. Expired/consumed challenges removed within 24 hours; expired/revoked session records within seven days. If a pending verification email needs the plaintext code, seal its outbox payload with a managed application key and purge it on send/expiry. No plaintext code in logs or routine DB fields. |
| Pending email payload | Minimize stored content; encrypt secret-bearing payloads, restrict access and expire with the job. Purge sensitive payload after acceptance/cancellation/expiry; retain metadata only. Never persist full reminder content for analytics. |
| Delivery/event metadata | Provider message/event ID, type/status and timestamps, at most 30 days. Avoid storing full webhook bodies, recipient addresses and email contents in general logs. |
| Application/proxy operational logs | At most 14 days, bounded/rotated, redacted; no request bodies, cookies, codes, email addresses, birth dates or personal totals. Redact token-bearing query/path values at the edge and application, including unsubscribe access. Document any Cloudflare/provider access metadata separately. |
| Suppression and deletion markers | Minimal keyed email identifier/account ID plus reason/time; no profile or mail content. Retain while needed to prevent re-sends and account resurrection, review annually. Disclose residual identifiers and protect the key separately; a keyed identifier is not claimed anonymous. |
| Backups | Encrypted off-instance daily backups, rolling 30-day retention. Deleted data can remain until backup expiry; before restored services accept traffic or send email, replay the independently retained deletion/suppression ledger and invalidate restored sessions/challenges/jobs. Document email-provider retention and deletion capabilities before launch; do not promise application deletion erases delivered messages or all processor logs. |

Processors and trust boundaries: Cloudflare terminates/proxies public traffic; EC2/PostgreSQL store account data; Resend receives destination email and rendered mail content. Reminder content can reveal personal age/horizon indirectly even without a literal birth date; disclose this before enrollment. Guest settings are not uploaded without an explicit import. Privacy wording must distinguish anonymous guest behavior, signed-in sync, reminder enrollment and existing downloaded images/offline caches. No end-to-end encryption claim: the backend must read settings to generate reminders.

## API contract surface

Canonical base: `https://aion.agape.engineering/api/v1`. UI remains at `/`, Spanish entry at `/es`. API routes are handled before SPA fallback; unknown API paths return JSON 404, never HTML. Authentication/CSRF exceptions are limited to challenge endpoints and narrowly verified webhook/unsubscribe capabilities. Native clients may use this API in a later release; native token flows are not implicitly implemented by browser-cookie auth.

| Operations | Purpose |
| --- | --- |
| `POST /auth/challenges`, `POST /auth/verify` | Request code / verify and establish a session; return challenge ID without exposing account existence. |
| `POST /auth/reverify` | Verify a new challenge bound to the existing user/session for sensitive operations; issuing uses a distinct challenge purpose. |
| `GET /me`, `POST /auth/logout`, `GET /sessions`, `DELETE /sessions/{id}` | Current identity, logout, list/revoke own sessions; revoke-all also supported with current-session behavior explicit. |
| `GET /profile`, `PUT /profile`, `DELETE /profile` | Read/create/update/reset owned profile; revision precondition required, including create-if-absent. |
| `GET /reminders`, `PUT /reminders` | Read/update enrollment, schedule and phrase preferences; require current revision. |
| `GET /account/export`, `DELETE /account` | Re-verified export and confirmed deletion. |
| `GET /unsubscribe`, `POST /unsubscribe`, `POST /webhooks/resend` | Confirmation, scoped opt-out and signature-verified provider events. |
| `/health/live`, `/health/ready` | Minimal liveness/readiness without credentials, personal data, versions or internal topology. Worker heartbeat/lag is monitored separately. |

Expected errors: 401 expired/missing session; 403 failed CSRF/authorization or required re-verification; 409 revision conflict; 422 field validation; 429 rate limiting with retry guidance; 503 temporary service unavailable. EN/ES presentation uses stable error codes. Wrong/expired/replayed verification must not authenticate or reveal another account's state. A complete generated FastAPI OpenAPI export and HTTP examples are implementation artifacts, reviewed in CI; this operation inventory is not a competing hand-maintained schema.

## Implementation sequence and release gates

1. **Behavior and design accepted (2026-10-17):** this amendment and ADR-0002 are the implementation baseline. Align active product/agent instructions and requirement mappings; prepare the account UI prototype and API examples before affected implementation. Keep R1 historical records intact. Acceptance alone is not implementation, test or deployment evidence.
2. **Accounts and backend foundation:** select/pin compatible maintained security components; code/prototype verified signup/session/reverification and account lifecycle; real-Postgres migrations and two-user tests. Prepare Compose, configuration inventory and host readiness/cost/recovery plan. Account functions stay disabled publicly until privacy and retention safeguards are ready.
3. **Sync:** profile validation/calendar parity, explicit import, scoped local caches, revision conflicts/offline replay and reset. Verify two-device and two-account journeys, including expired sessions, stale writes and denial of cross-account access.
4. **Reminders:** single shared phrase source; consent/preferences, timezone rules, durable outbox/worker, templates/unsubscribe/signed webhooks, suppression and deletion barriers. Configure selected email team/domain/keys/DNS under the approved rollout; perform only controlled integration sends until release gates pass.
5. **Release and cutover:** immutable images and exact-source CI; database/backup/restore/rollback rehearsal; privacy and support copy; account isolation and live synthetic account/mail smoke; DNS/TLS/API-cache checks and preserved static fallback. Verify first due reminder and unsubscribe, observe worker/API/backup health and record actual evidence. No migration or email claim based on a plan alone.

### Implementation scope and remaining operational inputs

The accepted baseline selects optional email-code accounts, explicit profile sync, reminder defaults, data-retention/recovery targets, same-origin API and the EC2/Resend architecture. It permits preparing the full implementation and provider/deployment configuration within the agreed rollout. Record the actual host/account/region, provider team and plan, support mailbox, secret references, monthly incremental costs and release evidence before the corresponding external mutation. Unspecified purchases/paid upgrades, destructive host actions or unrelated migrations are not implied by a product specification. Use existing configured access rather than requesting duplicate accounts; resolve missing access or material cost decisions against the concrete prepared configuration.

These are operational prerequisites, not evidence that a host exists or a provider supports a particular unverified plan. Public docs identify roles/configuration names, never private account identities, credentials or internal planning mappings.
